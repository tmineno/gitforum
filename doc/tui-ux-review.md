# TUI の探索的 UX レビュー手順

エージェントが `git-forum tui` を利用者として操作し、使いにくさや分かりにくさを報告書にまとめるための手順。仕様は `doc/spec/TUI-UX-TESTING.md` の「B. AI による探索的 UX レビュー」。CI のゲートではなく、手元で随時実行する。

## 守ること

- **TUI はドライバ `scripts/tui-ux/drive.py` を通してだけ起動する。** 手元のリポジトリで `git forum tui` を直接起動しない。git-forum へ書き込むコマンド（`git forum new` など）も実行しない。このリポジトリには、TUI から誤って作られて却下されたスレッドが既に 3 件ある。
- **git-forum に起票しない。** 起票するのは、報告を読んだ利用者が選んだ指摘だけで、利用者の指示を受けてから別途行う。
- 書き込むのは `./tmp/` の下だけ。
- 重いコマンド（`cargo build`、`cargo test`）は、共有マシンの決まりに従い `box-lease run --shared` で実行する。

## 準備

1. 出力先を決める: `R=tmp/tui-ux-review/$(date +%Y%m%d-%H%M%S)`。以降のファイルはすべて `$R` の下に置く。
2. バイナリとテストバイナリをビルドする: `cargo build` と `cargo test --lib --no-run`。ドライバは実行のたびにテストのフィクスチャ（不変条件スイートと同じもの）を cargo で書き出すので、テストバイナリが必要。
3. 手元のリポジトリの状態を記録する: `git for-each-ref refs/forum > $R/refs-before.txt`。
4. ドライバの動作を確かめる: `scripts/tui-ux/selftest.sh`。すべて `ok` にならなければレビューを始めず、結果をそのまま報告する。

## ドライバの使い方

```
uv run scripts/tui-ux/drive.py --bin target/debug/git-forum --fixture full \
  --size 80x24 --keys $R/keys/F1.keys --out $R/runs/F1-a
```

- `--fixture`: `full`（25 スレッド。lifecycle・状態・ノード種別・返信・リンク・長い本文・Markdown の表・日本語・絵文字を含む）か `empty`（スレッドなし）。スレッドとノードの ID と日時は毎回同じ。
- 実行のたびにフィクスチャから新しいリポジトリを作る。前の実行の操作は残らないので、キー列ファイルには起動直後からの操作をすべて書く。
- 出力: `step-000.txt`（起動直後の画面）、操作ごとの `step-NNN.txt`、その横の `step-NNN.hl.txt`、`run.json`（キー列、端末サイズ、バイナリのバージョン、終了コード、標準エラー出力、タイムアウトの有無、操作ごとの画面が落ち着くまでの時間）。
- `step-NNN.txt` は画面の文字だけで、色は入らない。TUI は選択中の行を背景色で示すので、選択の位置は `step-NNN.hl.txt` で確かめる。背景色付きか反転表示のセルが続く範囲ごとに `<行>,<開始桁>-<終了桁>: <文字>` の 1 行がある。「押しても何も変わらない」と判断する前に、`.hl.txt` も比べる。
- 終了コード: 0 は正常。1 は画面が落ち着かなかった（`run.json` の `timeout`）か、TUI が 0 以外で終了した。2 は引数かキー列ファイルの誤り。
- キー列を最後まで送っても TUI が動いていれば、ドライバが Ctrl-C で終了させる（`run.json` の `quit_by_driver`）。
- ドライバの環境では、外部エディタは内容を変えずに終わる `true` に置き換えてあり、クリップボードのコマンドは PATH にない。`e` での外部エディタや `y` でのコピーの結果は、このレビューでは確かめられない。

### キー列ファイル

1 行に 1 操作。空行と `#` で始まる行は読み飛ばす。

| 書き方 | 意味 |
|---|---|
| `j`、`q`、`S` など 1 文字 | その文字のキー |
| `Enter`、`Esc`、`Tab`、`BackTab`、`Backspace`、`Delete`、`Space`、`Up`、`Down`、`Left`、`Right`、`Home`、`End`、`PageUp`、`PageDown` | 名前の付いたキー |
| `Ctrl-s` など | Ctrl と英小文字 |
| `text:<文字列>` | 文字列をまとめて入力する（`#` を打つときは `text:#`） |
| `resize:<W>x<H>` | 端末サイズを変える |
| `click:<x>,<y>` | 左クリック（押して離す） |
| `dblclick:<x>,<y>` | ダブルクリック |
| `scroll:up@<x>,<y>` / `scroll:down@<x>,<y>` | ホイール |

座標は `step-NNN.txt` の桁と行で、どちらも 0 から数える。

## 課題

利用者として次の課題を行う。操作方法は画面のヘルプ行から探し、このリポジトリのソースは読まない（ソースを読むと、利用者が迷う点に気付けない）。

1. execution のスレッドを、題名・タグ・本文を付けて作る。
2. 既存の proposal に objection を付け、それを解決する。
3. フィルタを使って、状態が working のスレッドだけを表示する。
4. スレッドのノードから、別のスレッドへリンクを張る。
5. マウスだけで、スレッドを開いて戻る。キーでできてマウスでできないことを探す。
6. 課題 1 と 3 を 60×20 でも行う。

端末サイズは 80×24（不変条件 INV-2 が保証する最小サイズ）と 60×20 の 2 種類。60×20 は不変条件の対象外なので、表示が欠けていても、課題をやり遂げられるかどうかで判断する。

## 点検項目

指摘には、次のどれに当たるかを ID で書く。

| ID | 点検項目 |
|---|---|
| C1 | キーの見つけやすさ（必要な操作がヘルプ行から分かるか） |
| C2 | ヘルプ行に書かれたキーが実際に効くか |
| C3 | 戻る・取り消しの文言の一貫性 |
| C4 | 操作に対する反応の有無（押しても何も変わらない、変わったことが分からない） |
| C5 | 狭い幅での表示の欠け |
| C6 | 日本語など全角文字の表示崩れ |
| C7 | エラーメッセージから次の手が分かるか |
| C8 | 取り消せない操作の前に確認があるか |
| C9 | マウスでできることとキーでできることの差 |
| C10 | クリックできそうに見えて反応しない表示 |

## 報告

### findings.json

指摘はまず `$R/findings.json` に書く。確認スクリプトはこのファイルを読む。

```json
{
  "findings": [
    {
      "id": "F1",
      "severity": "major",
      "check": "C4",
      "title": "一文で書いた指摘",
      "keys": "tmp/tui-ux-review/20260923-150000/keys/F1.keys",
      "size": "80x24",
      "fixture": "full",
      "step": 3,
      "quote": "step-003.txt にある文字列（1 行の中の一部でよい）",
      "observation": "何をして、画面に何が出たか",
      "suggestion": "改善案"
    }
  ]
}
```

- `severity`: `blocker`（課題をやり遂げられない）、`major`（やり遂げられるが、多くの利用者が迷う・誤る）、`minor`（迷うが自力で気付ける）、`nit`（表記や見た目の細部）。
- `keys`: その指摘を起動直後から再現するキー列ファイル。指摘ごとに 1 つ作る。
- `quote`: 根拠となる画面の文字列。`step` の画面のどれか 1 行に含まれていなければならない。複数ある場合は文字列の配列にする。画面に出ないこと（何も表示されない、など）を指摘する場合は、その状態を示す画面の行（例: 操作後も変わらないヘルプ行）を引用する。

### 報告前の確認

```
uv run scripts/tui-ux/verify.py --bin target/debug/git-forum \
  --findings $R/findings.json --out $R/verify
```

指摘ごとにキー列を再生し直し、引用が画面にあるかを確かめて `引用行あり` / `引用行なし` / `再生失敗` を出す。`引用行あり` にならなかった指摘は本文に入れず、報告の「未確認」の節に理由とともに並べる。未確認の指摘は起票の候補にしない。

### report.md

`$R/report.md` に次の順で書く。

1. 概要: 行った課題、端末サイズ、バイナリのバージョン（`run.json` の `version`）、指摘の件数（重大度別）。
2. 指摘（`引用行あり` のものだけ、重大度の高い順）: ID、重大度、点検項目、題、観察した内容と `step-NNN.txt` からの引用、再現用のキー列ファイルと端末サイズ、改善案。
3. 未確認: 確認スクリプトで `引用行あり` にならなかった指摘と、その結果。
4. ドライバの問題: タイムアウトや起動の失敗があれば、そのまま書く（応答しない画面は UX の問題でもある）。

## 終了時

1. `git for-each-ref refs/forum > $R/refs-after.txt` を取り、`refs-before.txt` と比べる。違いがあれば、報告の冒頭にそのことを書き、利用者に知らせる。
2. 端末には、指摘の件数（重大度別）、上位の指摘の題、`report.md` の場所だけを書く。
3. ホームディレクトリのパスやユーザー名を報告に書かない（パスは `./tmp/...` のように書く）。
