# Feature: TUI UX Testing

> **Status:** Draft · Spec-driven kickoff · 2026-09-23
> **Owner:** maintainer
> **Related:** SPEC-3.0 §7.1（TUI surface）、`doc/spec/TEST-POLICY.md`、`doc/adr/012-tui-ux-testing-layers.md`、`scripts/demo/record.py`（実バイナリを PTY で操作する既存の例）、CI 新設チケット `6ncwev44`

## Goal

TUI の使い勝手に関する約束を、次の 2 つの手段で自動的に確かめられるようにする。

1. **不変条件スイート（CI 用）**: `cargo test` の中で、生成したキー入力・マウス操作・端末リサイズの列を、フィクスチャのリポジトリを開いた TUI に流す。本番のイベントループと同じ処理経路を通し、下記 INV-1〜INV-8 のどれかが破れたら失敗する。失敗時は、最小化した操作列・端末サイズ・その時点の画面を出力し、同じ失敗をそのまま再現できる。
2. **AI による探索的 UX レビュー（手元用）**: 開発者がエージェントに `doc/tui-ux-review.md` の手順を実行させる。エージェントは実バイナリの `git-forum tui` を使い捨てのリポジトリ上で PTY 越しに操作し、使いにくさや分かりにくさの指摘を報告書にまとめる。各指摘には、ドライバで再生できるキー列と、根拠となる画面の記録が付く。

現状の TUI のユニットテスト（`src/internal/tui/mod.rs`）は `handle_key` を直接呼ぶため、`run_app` にある破棄確認とエラー表示の分岐はテストから通らない。操作列を網羅的に試す仕組みも、利用者の立場で UX を点検する手順もない。

## Non-goals

- **画面全体の golden スナップショット比較。** 表示の細部を変えるたびに大量の更新が必要になるため採らない。見た目の良し悪しは AI レビューで扱う。
- **実バイナリの PTY E2E を CI ゲートにすること。** 実端末に固有の挙動（raw mode、代替画面、外部エディタ、クリップボード）は AI レビューと手動確認の範囲とする（ADR-012）。
- **CI の新設。** GitHub Actions の workflow（fmt → clippy → check → test、失敗時はマージ不可）は別チケット `6ncwev44` で先に作る。この spec が扱うのは「`cargo test` で不変条件スイートが走る」ところまで。
- **見つかった UX 不具合の修正。** 不変条件の違反も AI レビューの指摘も、1 件ずつ別チケットで直す。
- **AI レビューの指摘を git-forum へ自動で起票すること。** 起票するのは利用者が承認した指摘だけ。
- **ヘルプ行に書かれたキーが実際に効くかの CI 検査。** 「効いた」の判定に解釈が入るため、AI レビューの点検項目として扱う。
- **TUI の描画性能や応答時間の測定。**

## Inputs / Outputs

### 用語

- **モード**: 入力の解釈を決める状態。`View`（List / ThreadDetail / NodeDetail / CreateThread / EditThreadBody / CreateNode / EditNodeBody / CreateLink）に、List のフィルタバー表示中、テキスト選択モード（`S` キー）、破棄確認、エラー表示の 4 つを加えたもの。
- **フォームの未保存入力**: 作成フォームで利用者が打ち込んだ自由記述のテキスト。スレッドのタイトル・タグ・本文、ノードの本文、手入力のリンク先が該当する。一覧から選ぶ項目（lifecycle、ノード種別、リンクの relation など）は含めない。現行の `has_unsaved_form_input` はタグを見ていないので、この定義とは一致しない。

### A. 不変条件スイート

**入力**

- **フィクスチャのリポジトリ**: テンプレートを 1 度だけ `StepClock`（`src/internal/clock.rs`）で作り、ケースごとに一時ディレクトリへ複製して使う。操作がスレッドの作成やノードの解決でリポジトリを書き換えるため、ケース間で状態を持ち越さない。テンプレートには次を必ず含める。
  - lifecycle 3 種（proposal / execution / record）と、複数の status のスレッド
  - 各種ノード（comment / objection / action など）と、返信の入れ子
  - スレッド間のリンク
  - ビューポートより長い本文、Markdown の表、CJK 文字と絵文字を含むタイトルと本文
  - これとは別に、スレッドが 0 件のリポジトリ
- **操作の種類**:
  - キー: `input.rs` が扱う全キー（`q Q j k f c r y l m S z t e x o R`、Space、Enter、Esc、Tab、Backspace、矢印、PageUp/PageDown/Home/End、Ctrl-S、Ctrl-C）と、フォーム入力用に、どのキーにも割り当てられていない文字（ASCII と CJK）
  - マウス: 左クリック、ホイール、ドラッグ。座標は、描画時に記録されたクリック領域（`UiRects`）の内側を優先して選び、フレーム内の任意の点も混ぜる
  - リサイズ: 端末サイズの集合 S の中での変更
  - 深いモードに入るための定型の操作列（例: `c` → Tab ×3 → Enter で EditThreadBody）を、生成する操作列の先頭に混ぜる
- **端末サイズの集合 S**: 少なくとも 1×1、各モードの最長のヘルプ行より狭い幅、80×24、200×60 を含む。
- **ケース数**: 既定値は CI の所要時間の予算から決める（Performance / Safety を参照）。手元では `PROPTEST_CASES` で増やして長く回せる。

**テスト用の内部構造（公開 API ではない）**

- `run_app` にあるイベント 1 件分の処理（info 表示の消去、破棄確認の y/n、エラー表示の解除、`handle_key`/`handle_mouse` の呼び出し、エラーからエラー表示への変換）を 1 つの関数（以下 `dispatch_event`）に切り出す。戻り値は「継続」「終了」「外部エディタの要求（thread id つき）」のいずれか。`run_app` はこの関数だけを呼び、外部エディタの起動と自動更新は `run_app` 側に残す。挙動は変えない。
- 外部への副作用（クリップボードへのコピー、マウスキャプチャの切り替えによる標準出力への書き込み）を差し替えられるようにする。本番は現行どおりの実装を、テストは呼び出しを記録するだけの実装を使う。
- 不変条件の検査関数は、描画後の画面バッファ、アプリの状態、直前のイベント、`dispatch_event` の戻り値を受け取る純粋関数とする。
- スイートは `src/internal/tui/` 配下の `#[cfg(test)]` モジュールに置く。TUI の内部モジュールは crate の外から見えず、`TEST-POLICY.md` の対象は `tests/` だけであるため。

**不変条件**（操作 1 件を処理して再描画するたびに確かめる）

| ID | 内容 |
|---|---|
| INV-1 | イベント処理と描画が panic しない。 |
| INV-2 | 退出・解除のヒントが見える: 端末が 80×24 以上のとき、現在のモードに対応する表 H の文字列が、画面のどこかの 1 行に途切れずに表示されている。2026-09-23 時点では、ヒントが終わる位置は List と詳細ビューで 12 桁目まで、フォームとフィルタバーで 58 桁目まで。 |
| INV-3 | Esc で戻れる: どの状態からでも、次の手順を最大 K = 10 回繰り返せば、オーバーレイのない List に戻る。手順: エラー表示中またはテキスト選択モード中なら任意のキー、破棄確認中なら `y`、それ以外なら Esc。現行で最も長い戻り方は EditNodeBody からの 4 手（Esc → Esc → `y` → Esc）なので、K はその 2 倍以上に取っている。 |
| INV-4 | Esc と Ctrl-C での終了: Esc を処理した結果が「終了」になることはない。Ctrl-C は、フォームに未保存の入力があっても確認なしで終了する。ただし破棄確認中とエラー表示中は、1 回目の Ctrl-C はオーバーレイを閉じるだけで、2 回目で終了する。したがって、どの状態からでも Ctrl-C を最大 2 回押せば必ず「終了」になる。 |
| INV-5 | 未保存入力を黙って捨てない: フォームの未保存入力がある状態から、1 回のイベントで作成フォーム群（CreateThread / EditThreadBody / CreateNode / EditNodeBody / CreateLink）の外へ出たなら、そのイベントは「送信の成功」か「破棄確認中の `y`/`Y`」のどちらかである。Ctrl-C による終了は INV-4 のとおり確認なしでよいので、この検査の対象外とする。 |
| INV-6 | 選択とスクロールが範囲内: 一覧の選択は、表示行が 0 件なら None、それ以外なら表示件数未満。ノード表の選択は、表示されている行（先頭のスレッド本体の行を含む）の範囲内。テキストが空でないペインは、どのスクロール位置でも、枠の内側に空白以外の文字を 1 文字以上表示する。 |
| INV-7 | クリック領域がフレーム内: 描画後に `UiRects` に記録された領域は、すべてフレームの内側に収まる。 |
| INV-8 | オーバーレイの解除: エラー表示中のキー入力（Ctrl-C を含む）は表示を消すだけで、ビュー・フォーム・選択を変えない。破棄確認中は、`y`/`Y` なら入力を破棄して移動し、それ以外のキー（Ctrl-C を含む）なら確認を閉じてフォームの内容を保つ。 |

表 H（2026-09-23 時点のヘルプ行とオーバーレイの文言から転記した。文言を変えたら、この表も同じコミットで更新する）

| モード | 表示されるべき文字列 |
|---|---|
| List | `[q]quit` |
| List（フィルタバー表示中） | `[esc]cancel` |
| ThreadDetail / NodeDetail | `[esc/q]back` |
| CreateThread / CreateNode / CreateLink | `[esc]cancel` |
| EditThreadBody / EditNodeBody | `[esc]back` |
| テキスト選択モード | `press any key to return` |
| 破棄確認 | `Press y to discard, any other key to cancel` |
| エラー表示 | `Press any key to dismiss` |

**出力**

- 成否。失敗時は、違反した不変条件の ID、最小化した操作列、端末サイズ、再現用のシード、違反した時点の画面テキストを出す。proptest が書き出す回帰用シードのファイルはコミットする。
- 実行ごとの、モード別の到達回数の集計。
- **既知の違反の除外リスト**: スイートの導入時点で既に破れている不変条件は、テストコード内のリストに「不変条件の ID・条件・最小の再現操作列・git-forum のチケット ID」の組で登録し、検査から除く。

### B. AI による探索的 UX レビュー

**入力**

- **ドライバ** `scripts/tui-ux/drive.py`（uv script。依存は `scripts/demo/record.py` と同じ版の pexpect と pyte）
  - 引数: git-forum のバイナリ、フィクスチャ名、端末サイズ、キー列ファイル、出力ディレクトリ
  - 実行のたびに、`./tmp/` の下へ使い捨てのリポジトリを新しく作る。`scripts/demo/record.py` と同様に個人の Git 設定を読まない環境変数（`GIT_CONFIG_GLOBAL=/dev/null` など）を設定し、クリップボードのコマンドを含まない `PATH` で、`git-forum tui` を PTY 上に起動する。既存のリポジトリを指定する引数は持たない。
  - キー列ファイルは 1 行に 1 操作: キー名（`j`、`Enter`、`Esc`、`Ctrl-s` など）、`text:<文字列>`、`resize:<W>x<H>`、`click:<x>,<y>`、`scroll:up@<x>,<y>` / `scroll:down@<x>,<y>`。
  - 操作のたびに、画面の変化が止まるまで待つ。待ち時間の閾値は実装時に計測して決める。
- **手順書** `doc/tui-ux-review.md`。エージェント向けに次を定める。
  - 利用者として行う課題（例: execution のスレッドを作る、objection を付けて解決する、フィルタで目的のスレッドを探す、ノードからリンクを張る）
  - 点検項目: キーの見つけやすさ、ヘルプ行に書かれたキーが実際に効くか、戻る/取り消しの文言の一貫性、操作に対する反応の有無、狭い幅での表示の欠け、CJK の表示崩れ、エラーメッセージから次の手が分かるか、取り消せない操作の前に確認があるか
  - 端末サイズ: 80×24（INV-2 が保証する最小サイズ）と、それより狭い 60×20 の 2 種類。狭い幅は不変条件の対象外だが、表示が欠けても使えるかを判断するために見る
  - 報告の書式と、報告前の確認手順（Failure modes 9）

**出力**

- ドライバ: 出力ディレクトリに、操作ごとの画面テキスト `step-NNN.txt`（`step-000.txt` は起動直後）と、実行記録 `run.json`（キー列、端末サイズ、バイナリのバージョン、フィクスチャ名、終了コード、標準エラー出力、タイムアウトの有無）。
- レビュー: `./tmp/tui-ux-review/<日時>/report.md` と、端末への要約。指摘ごとに、ID、重大度（blocker / major / minor / nit）、該当する点検項目、観察した内容（`step-NNN.txt` の該当行の引用）、再現用のキー列ファイルと端末サイズ、改善案を書く。
- git-forum へは書き込まない。利用者が選んだ指摘だけを、別途 `--as ai/<agent>` で起票する。

### Public API surface

なし。CLI のフラグ、サブコマンド、設定キーは増やさない。`dispatch_event` と副作用の差し替え口は `src/internal/tui/` の非公開要素とする。dev-dependency に `proptest` を加える。

## Failure modes

1. **導入時点の既存違反でスイートが失敗する**
   - (a) 契機: 現行コードが不変条件を満たしていない。
   - (b) 検出: スイートの失敗。
   - (c) 見え方: マージできない。
   - (d) 対処: 違反ごとにチケットを起票し、除外リストに登録する。登録した最小再現操作列は毎回そのまま再生し、違反が再現しなくなったら「除外が古い」としてテストを失敗させる。除外が残り続けて問題が見えなくなるのを防ぐため。
2. **一部のモードに到達せず、検査が効いていない**
   - (a) 契機: ランダムな操作列では、EditNodeBody や破棄確認のような深いモードにほとんど入らない。
   - (b) 検出: モード別の到達回数の集計。
   - (c) 見え方: 既定のケース数で到達回数が 0 のモードがあれば、テストが失敗する。
   - (d) 対処: 定型の前置き操作列を生成器に加える。
3. **検査関数の誤りで違反を見逃す**
   - (a) 契機: 不変条件を判定するコードの誤り。
   - (b) 検出: 検査関数ごとの自己テスト（AT-2）。違反する状態を手で作って渡し、違反と判定されることを確かめる。
   - (c) 見え方: 自己テストの失敗。
   - (d) 対処: 自己テストが通るまでスイートの結果を信用しない。
4. **テストの経路と本番の経路がずれる**
   - (a) 契機: `run_app` が `dispatch_event` を通さずに入力を処理するコードを持つ。
   - (b) 検出: ソースを走査する監査テスト（AT-6）。既存の `syn` を使う監査テストと同じ方式。
   - (c) 見え方: 監査テストの失敗。
   - (d) 対処: 入力処理を `dispatch_event` に戻す。
5. **テストが開発者の環境に副作用を出す**
   - (a) 契機: `y` による開発者のクリップボードの上書き。`S` などでマウスキャプチャを切り替えるエスケープシーケンスが、`cargo test` を実行中の端末へ直接書かれる（テストハーネスは `print!` しか捕捉しない）。外部エディタの起動。開発者のリポジトリへの TUI 状態ファイルの保存。
   - (b) 検出: 監査テスト（AT-6）と、記録用の副作用実装への呼び出しの記録（AT-7）。
   - (c) 見え方: 起きれば、テスト後に開発者のクリップボードや端末の状態が変わる。
   - (d) 対処: 副作用は差し替え口を通す。TUI 状態ファイルのパスは一時ディレクトリに向け、外部エディタの要求は `dispatch_event` の戻り値として返すだけにする。
6. **結果が実行のたびに変わる**
   - (a) 契機: 自動更新の時刻依存、`HashSet` の走査順、環境変数、実時刻。
   - (b) 検出: 同じシードで 2 回実行した結果の比較（AT-8）。
   - (c) 見え方: CI が不安定になる。
   - (d) 対処: `dispatch_event` に自動更新を含めない。フィクスチャは `StepClock` で作る。ケースの途中で TUI が作るスレッドの時刻は実時刻になるが、不変条件は時刻の表示に依存しない。
7. **CI の所要時間が予算を超える**
   - (a) 契機: ケース数 ×（フィクスチャの複製 + 操作の処理）。
   - (b) 検出: CI の実行時間。
   - (c) 見え方: マージまでの待ち時間が延びる。
   - (d) 対処: 既定のケース数を下げ、長い探索は手元で `PROPTEST_CASES` を上げて行う。
8. **ドライバが起動しない、または画面が落ち着かない**
   - (a) 契機: バイナリがない、uv や依存を入れられない、TUI が描画し続ける。
   - (b) 検出: ドライバの終了コードと `run.json`。
   - (c) 見え方: 待ち時間の上限を超えたら、その時点の画面を保存し、`run.json` に timeout と記録して非 0 で終了する。
   - (d) 対処: エージェントは timeout そのものを指摘として報告する（応答しない画面は UX 上の問題でもある）。
9. **AI レビューが根拠のない指摘をする**
   - (a) 契機: 画面にない内容を指摘する、再現しない指摘を書く。
   - (b) 検出: 報告の前に、指摘ごとに再現用のキー列をドライバで再生し、引用した行が該当の `step-NNN.txt` にあることをスクリプトで確かめる。
   - (c) 見え方: 確かめられなかった指摘は本文から外し、「未確認」の節に分けて列挙する。
   - (d) 対処: 未確認の指摘は起票の候補にしない。
10. **AI レビューが開発者のリポジトリに書き込む**
    - (a) 契機: エージェントが手元のリポジトリで直接 `git forum tui` を起動する。このリポジトリには、`Created in TUI` という題で作られ却下されたスレッドが 3 件ある（`vmv1l4st`、`wj05n02e`、`itqtdgtp`）。
    - (b) 検出: レビューの前後で、開発者のリポジトリの `git for-each-ref refs/forum` の出力を比べる。
    - (c) 見え方: 一致しなければ、報告の冒頭にその旨を書き、利用者に知らせる。
    - (d) 対処: 手順書は、ドライバを通さない起動を禁じる。

## Performance / Safety

- **CI の所要時間**: 予算は、スライス 3（proptest のハーネス）で 1 ケースあたりの処理時間を計測してから決め、決めた予算と既定のケース数をこの節に書き込む。参考として、2026-09-23 時点の `cargo test` 全体の所要時間は 4.18〜4.25 秒だった（`eae18e1`、ビルド済みの状態、32 コアの開発機を占有して 3 回計測）。CI のランナーはコア数が少なく、キャッシュがなければビルドも毎回かかるので、この値はそのまま CI には当てはまらない。
- **決定性**: 同じシードとケース数なら、同じ操作列が生成され、同じ判定になる。
- **開発者環境の保護**: 不変条件スイートは、開発者のクリップボード、端末、外部エディタ、リポジトリに触れない。AI レビューは `./tmp/` の外に書き込まない。
- **匿名化**: 指摘を起票するときは、報告に含まれるホームディレクトリのパスやユーザー名をマスクする。

## Acceptance tests

1. **AT-1 スイートが通る**: 除外リストを含めた状態で、不変条件スイートのテスト（`cargo test` でモジュール名を指定して実行）が成功する。除外リストのどの項目にも git-forum のチケット ID が付いている。
2. **AT-2 検査関数の自己テスト**: INV-2〜INV-8 のそれぞれについて、違反する画面バッファや状態を手で組み立てて検査関数に渡すと、その INV の違反として報告される。例: 一覧の選択を表示件数と同じ値にする → INV-6。表 H の文字列を含まない List の画面 → INV-2。INV-1 は、panic する描画関数を渡すと違反として報告されることで確かめる。
3. **AT-3 全モードに到達する**: 既定のケース数の実行で、「用語」に挙げたモード（List、フィルタバー、ThreadDetail、NodeDetail、CreateThread、EditThreadBody、CreateNode、EditNodeBody、CreateLink、テキスト選択、破棄確認、エラー表示）のすべてに 1 回以上到達する。到達しないモードがあればテストが失敗する。
4. **AT-4 失敗時の出力**: 手元で ThreadDetail の Esc を無効にする変更を一時的に入れて実行すると、INV-3 の違反として、最小化した操作列、端末サイズ、シード、画面テキストが出力される。変更を戻すと成功する。手動の確認として、実行結果を PR に記録する。
5. **AT-5 挙動を変えない切り出し**: `dispatch_event` を切り出したあと、既存の TUI ユニットテストが変更なしですべて通る（切り出し前の件数を記録し、同数であることを確かめる）。INV-8 の各場合（エラー表示中の任意のキー、破棄確認中の `y`、`Y`、その他のキー）を `dispatch_event` 経由で確かめる個別のテストが通る。

7. **AT-7 副作用の記録**: スイートの環境で、List でスレッドを選んで `y` を押すと、記録用の実装にクリップボードの呼び出しが 1 件（`@<id>`）残る。ThreadDetail で `S` を押すとマウスキャプチャ無効化の呼び出しが 1 件残り、続けて任意のキーを押すと有効化の呼び出しが 1 件残る。

9. **AT-9 古い除外の検出**: 実際には違反しない操作列を持つ項目を除外リストに加えると、テストが「除外が古い」という理由で失敗する。
