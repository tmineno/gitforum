# Feature: Large Forum Reads

> **Status:** Accepted · 2026-09-26
> **Owner:** maintainer
> **Related:** ADR-015（読み取りを `git cat-file --batch` 1 本にまとめる）、`doc/spec/archive/SPEC.md`（git は plumbing コマンドをサブプロセスで呼び、libgit2 は使わない）、`tests/cli_node_show_perf_test.rs`（bug `bvdk2w48`）、`doc/spec/TUI-UX-TESTING.md`

## Goal

スレッドが数百件あるリポジトリでも、スレッド一覧を読む操作（`ls`、`shortlog`、TUI の起動、TUI の一覧の自動更新）と、ノード ID からスレッドを探す操作（`node show` など）が、スレッド数に比例した数の `git` プロセスを起動しない。1 回のコマンドで起動する `git` のプロセスの数は、スレッド数によらず同じになる。TUI の一覧の自動更新は、tip が変わったスレッドと新しく現れたスレッドだけを読む。CLI の出力と TUI の画面は変えない。

2026-09-26 時点では、スナップショットを 1 件読むたびに `ls-tree` を 1 回と、ファイル（`thread.toml`、`body.md`、ノードごとの `.toml` と `.md`、`links.toml`、`evidence.toml`）ごとに `cat-file` を 1 回起動している。`ls` はさらにスレッドごとに ref を `rev-parse` で解決し、`node show` はノードの持ち主を探すためにスレッドごとに `ls-tree` を起動する。TUI は 2 秒ごとに ref の変化を確かめ、1 つでも変わっていれば全スレッドを読み直す。openlt-rs の forum の ref（690 スレッド、2,758 ノード）を複製したリポジトリで、`master`（`4bfc137`）のリリースビルドを使い、他の作業と機械を共有した状態で測った値は次のとおり。

| 操作 | 時間（3 回） | `git` の起動回数 |
|---|---|---|
| `ls` | 23.36 / 23.29 / 23.58 s | 9,047（`cat-file` 7,660、`rev-parse` 694、`ls-tree` 690） |
| TUI の起動（一覧に件数が出るまで） | 7.09 / 7.11 s（2 回） | 8,360 |
| `node show <id>` | 2.34 / 2.49 / 2.75 s | 963（`ls-tree` 691、`cat-file` 264） |
| `show` / `brief --json` / `status`（ノード 67 件のスレッド） | 0.14〜0.48 s | 147 |

## Non-goals

- **書き込みの経路**（`new`、`say`、状態の変更など）の起動回数。書き込みは 1 件のスレッドにしか触れないので、スレッド数に比例しない。
- **git のライブラリ**（libgit2、gix）を入れること。ADR-015 の Alternatives を参照。
- **TUI の読み込みを描画のスレッドの外に移すこと**。読み込みの起動回数が一定になれば、描画を止める時間はスレッド数に比例しなくなる。
- **読み込んだ結果をディスクに保存すること**（SQLite の index はタスク `913c4s9v` で削除した）。
- **`doctor`、`publish`、`hook` などの全スレッドの走査で、スレッドごとに ref を解決している箇所**。これらもスナップショットの読み取りは速くなるが、ref の解決をまとめるのはこの spec の対象外とする。
- `ls` の出力の形式と並び順の変更。
- **SHA-256 のオブジェクト形式のリポジトリでの動作確認**。ツリーの解析はハッシュの長さを前提にしないように作るが、git-forum 自体がそのようなリポジトリで動くかは確かめず、テストもしない。
- **時間の目標値**。時間は機械の負荷で揺れるので、テストの合否には使わない。受け入れ条件は、起動回数がスレッド数によらないこと（AT-2〜AT-4）と、AT-9 の前後比較の記録とする。

## Inputs / Outputs

**入力**: `refs/forum/threads/*` と `refs/forum/published/*` が指すコミットのツリー（SPEC-3.0 §4.2 の配置）。

**出力**: 変えない。CLI の標準出力・標準エラー・終了コード、TUI の画面は、同じリポジトリに対して変更前と同じになる。例外は Failure modes の 2（壊れたリポジトリでのエラーの文言）だけ。

**振る舞いの変更**

1. **オブジェクトの読み取り**: `GitOps` は、最初の読み取りのときに `git cat-file --batch` を 1 本起動し、そのあとのファイルとツリーの読み取りはすべてこのプロセスに送る。起動のしかた（作業ディレクトリ、取り除く環境変数 `GIT_DIR`・`GIT_WORK_TREE`・`GIT_INDEX_FILE`・`GIT_OBJECT_DIRECTORY`・`GIT_ALTERNATE_OBJECT_DIRECTORIES`）は、ほかの `git` の呼び出しと同じにする。`GitOps` を破棄するときは、このプロセスの標準入力を閉じ、終了を待つ。
2. **スナップショットの読み取り**（`read_snapshot_at`）: ファイルの一覧は、コミットのツリーを 1 の読み取りでたどって作る。一覧の中身は、今の `ls-tree -r --full-tree --name-only <commit>` と同じ（ファイルのパスだけ、ルートからの相対パス）。
3. **ノードの持ち主の索引**（`NodeIdIndex::build`）: `for-each-ref` を 1 回と、1 の読み取りで各スレッドの `nodes` ツリーを読む。
4. **スレッドの状態の一覧**（`list_thread_states`、`ls` と `shortlog` が使う）: スレッドごとに ref を解決せず、`for-each-ref` で得た tip を使う。authoritative の ref が published の ref より優先される規則（RFC `fls856j3` §5）は変えない。
5. **TUI の一覧の自動更新**: 前回読んだ行を、スレッドの ID・tip の SHA・published から読んだかどうかの 3 つを組にして覚えておく。更新のときは、この組が前回と同じスレッドは覚えている行を使い、それ以外のスレッドだけを読む。ref がなくなったスレッドは一覧から外す。スナップショットの中身はコミットの SHA で決まるので、覚えている行が古くなることはない。

**公開 API の追加・変更**（`git_forum::internal` は crate の外から使えるので、ここに挙げる）

- `GitOps::show_file(commit, path) -> ForumResult<String>` と `GitOps::show_file_bytes(commit, path) -> ForumResult<Vec<u8>>`（シグネチャは変えない）
  - 事前条件: `commit` はこのリポジトリのコミットを指す。
  - 事後条件: 今と同じ値を返す。`show_file` は内容を UTF-8 として（不正なバイトは置き換えて）読み、末尾の空白を落とした文字列。`show_file_bytes` はバイト列そのまま。
  - 失敗: `path` がない、またはファイルでないときは `ForumError::Git`。`git` を起動できないとき、プロセスが途中で終了したときも `ForumError::Git`。
  - 副作用: 最初の呼び出しで 1 のプロセスを起動する。
- `GitOps::list_tree_files(commit) -> ForumResult<Vec<String>>`（追加）
  - 事前条件: `commit` はこのリポジトリのコミットを指す。
  - 事後条件: `git ls-tree -r --full-tree --name-only <commit>` と同じパスを、同じ順に返す。
  - 失敗・副作用: `show_file` と同じ。
- `GitOps::spawned_processes() -> usize`（追加）
  - 事前条件: なし。
  - 事後条件: この `GitOps` が起動した `git` のプロセスの数を返す。1 のプロセスは 1 と数える。
  - 失敗: なし。
  - 副作用: なし。
  - この値のために、`GitOps` の中で `git` を起動する箇所は、すべて 1 つの関数を通す。

## Failure modes

1. **`git` を起動できない、または 1 のプロセスが途中で終了する**
   - 検出: 起動の失敗、またはパイプの書き込み・読み込みの失敗。
   - 挙動: `ForumError::Git` を返し、今の `git` の失敗と同じようにコマンドが失敗する。
   - 回復: 次の読み取りでプロセスを 1 回だけ起動し直す。それも失敗したら `ForumError::Git` を返す。
2. **ツリーには載っているのにファイルの中身がない**（壊れたリポジトリ）
   - 検出: 1 のプロセスが `missing` を返す。
   - 挙動: `ForumError::Git` を返す。エラーの種類は今と同じだが、文言は `cat-file -p` の標準エラーではなくなる。
3. **1 のプロセスを起動したあとに書き込まれたオブジェクトを読む**（TUI でノードを作った直後にそのスレッドを開く、など）
   - 検出: 1 のプロセスが `missing` を返す。
   - 挙動: その 1 件だけ、今までどおり `cat-file -p` を 1 回起動して読み直す。見つかればその値を返し、なければ 2 と同じエラーにする。これにより、`git cat-file --batch` が起動後に書かれたオブジェクトをどう扱うかに、正しさが左右されない。
4. **SHA-256 のリポジトリ**
   - ツリーのバイナリ形式では、オブジェクト名の長さがハッシュの種類で変わる（SHA-1 は 20 バイト、SHA-256 は 32 バイト）。
   - 1 のプロセスが返すオブジェクト名（16 進数）の長さからバイト数を決め、20 バイトを前提にしない。
   - git-forum が SHA-256 のリポジトリで動くかどうか自体は確かめない（Non-goals を参照）。
5. **ASCII 以外の文字を含むファイル名**: `ls-tree` は `core.quotePath` に従ってそのような名前を引用符で囲むが、ツリーを直接読むと生の名前になる。git-forum の書き込みはそのような名前を作らないので、違いが出るのは手で作ったツリーだけとする。
6. **複数のスレッドから同じ `GitOps` を使う**: 1 のプロセスへの要求は 1 つずつ順に送り、応答を取り違えない。
7. **忘れやすい点: リポジトリのサブディレクトリから実行する**。今の `ls-tree` は `--full-tree` を付けてルートからのパスにそろえている。ツリーを直接読む場合もルートからのパスになることを、サブディレクトリから `ls` を実行するテストで確かめる。

## Performance / Safety

- **`git` の起動回数**: スレッド一覧を読む操作（`ls`、`shortlog`、TUI の起動と一覧の更新）と `node show` について、スレッド数によらず同じになる。上限の値は実装後に測って、この節に記録する。
- **時間**: 目標値は置かない（Non-goals を参照）。openlt-rs の forum の ref の複製（690 スレッド）で、変更前（`4bfc137`）と変更後の時間と起動回数を、開発機を占有した状態で 2 回ずつ測り、この節に記録する。この複製は別プロジェクトのデータなので `./tmp/` にだけ置き、コミットしない。
- **メモリ**: TUI が覚える行は、表示している一覧と同じ件数に限る。1 のプロセスは読み取りのたびに内容を返すだけで、読んだ内容を溜めない。
- **安全性**: 読み取りだけを変える。保存されるデータ、ref、作業ツリーのファイルは変わらない。

## Acceptance tests

1. **AT-1 読み取り結果の一致**
   - 用意するスナップショット: すべての種類のファイル（`thread.toml`、`body.md`、本文あり・なしのノード、`links.toml`、`evidence.toml`）を持ち、本文の末尾に改行と空白があり、CJK 文字と絵文字を含む。
   - 確かめること: このスナップショットを `read_snapshot_at` で読んだ結果が、ファイルごとに `cat-file -p` と `ls-tree` を起動して読んだ結果と一致する。テストは後者の読み方を比較用に持つ。
   - `show_file`、`show_file_bytes`、`list_tree_files` のそれぞれも、`cat-file -p` と `ls-tree -r --full-tree --name-only` の結果と比べる。
2. **AT-2 一覧の起動回数がスレッド数によらない**（`tests/cli_read_scaling_test.rs`）
   - 用意するリポジトリ: スレッド 10 件のものと 40 件のもの（どちらも各スレッドにノード 3 件）。
   - 実行: 起動のたびに 1 行を書き足す `git` のラッパーを `PATH` の先頭に置いて、`git forum ls` と `git forum shortlog` を実行する。
   - 確かめること: 2 つのリポジトリで数えた起動回数が等しい。出力の行数はスレッド数に応じて変わる。
3. **AT-3 `node show` の起動回数がスレッド数によらない**: AT-2 と同じ 2 つのリポジトリで、`git forum node show <id>` の起動回数が等しい。
4. **AT-4 TUI の一覧の読み込みの起動回数がスレッド数によらない**: AT-2 と同じ 2 つのリポジトリで、`snapshot::list::list_threads` を呼ぶ前後の `GitOps::spawned_processes()` の差が等しい。
5. **AT-5 TUI の自動更新**
   - 手順: 一覧を表示したあと、次の 3 つを順に行い、そのつど自動更新を 1 回実行する。
     1. スレッドを 1 件選んでノードを足す。
     2. 新しいスレッドを 1 件作る。
     3. スレッドを 1 件選んで ref を消す。
   - 確かめること（毎回）:
     - 一覧が、その時点で `list_threads` を呼んだ結果と一致する。
     - 更新でスナップショットを読んだスレッドが、変わったスレッドだけである。更新の関数は、スナップショットを読んだスレッドの ID を返す。1 のプロセスへの読み取りは `git` の起動として数えられないので、起動回数ではこの点を確かめられないためである。
6. **AT-6 書き込み直後の読み取り**: 1 つの `GitOps` でスナップショットを読んで 1 のプロセスを起動したあと、同じ `GitOps` でノードを書き込み、もう一度そのスレッドを読むと、足したノードが含まれている。
7. **AT-7 サブディレクトリからの実行**: リポジトリのサブディレクトリで `git forum ls` を実行すると、ルートで実行したときと同じ出力になる。
8. **AT-8 プロセスの後始末**
   - 手順: `GitOps` で 1 回読み取ったあと、その `GitOps` を破棄する。
   - 確かめること: 1 のプロセスが終了している。テスト用に、そのプロセスの pid を取れるようにする。
9. **AT-9 openlt-rs の規模での計測**（手作業の計測。CI では回さない）
   - 対象: openlt-rs の forum の ref の複製。
   - 測る操作: `ls`、`node show`、TUI の起動（一覧に件数が出るまで）。
   - 測る値: 時間と `git` の起動回数を、変更前と変更後で、開発機を占有して 2 回ずつ。
   - 結果は Performance / Safety に記録する。
10. **AT-10 既存のテスト**: `cargo test` がすべて通る。`tests/cli_node_show_perf_test.rs` の時間の上限を含む。
