# Feature: TUI UX Testing

> **Status:** Draft · Spec-driven kickoff · 2026-09-23
> **Owner:** maintainer
> **Related:** SPEC-3.0 §7.1（TUI surface）、`doc/spec/TEST-POLICY.md`、`doc/adr/012-tui-ux-testing-layers.md`、`scripts/demo/record.py`（実バイナリを PTY で操作する既存の例）、CI 新設チケット `6ncwev44`

## Goal

TUI の使い勝手に関する約束を、次の 2 つの手段で自動的に確かめられるようにする。

1. **不変条件スイート（CI 用）**: `cargo test` の中で、生成したキー入力・マウス操作・端末リサイズの列を、フィクスチャのリポジトリを開いた TUI に流す。本番のイベントループと同じ処理経路を通し、下記 INV-1〜INV-13 のどれかが破れたら失敗する。INV-9〜INV-12 は、マウス操作による画面遷移がキー操作と食い違わないことを確かめる。INV-13 は、スクロールが本文の最後の行でちょうど止まることを確かめる。失敗時は、最小化した操作列・端末サイズ・その時点の画面を出力し、同じ失敗をそのまま再現できる。
2. **AI による探索的 UX レビュー（手元用）**: 開発者がエージェントに `doc/tui-ux-review.md` の手順を実行させる。エージェントは実バイナリの `git-forum tui` を使い捨てのリポジトリ上で PTY 越しに操作し、使いにくさや分かりにくさの指摘を報告書にまとめる。各指摘には、ドライバで再生できるキー列と、根拠となる画面の記録が付く。

現状の TUI のユニットテスト（`src/internal/tui/mod.rs`）は `handle_key` を直接呼ぶため、`run_app` にある破棄確認とエラー表示の分岐はテストから通らない。操作列を網羅的に試す仕組みも、利用者の立場で UX を点検する手順もない。

## Non-goals

- **画面全体の golden スナップショット比較。** 表示の細部を変えるたびに大量の更新が必要になるため採らない。見た目の良し悪しは AI レビューで扱う。
- **実バイナリの PTY E2E を CI ゲートにすること。** 実端末に固有の挙動（raw mode、代替画面、外部エディタ、クリップボード）は AI レビューと手動確認の範囲とする（ADR-012）。
- **CI の新設。** GitHub Actions の workflow（fmt → clippy → check → test、失敗時はマージ不可）は別チケット `6ncwev44` で先に作る。この spec が扱うのは「`cargo test` で不変条件スイートが走る」ところまで。
- **見つかった UX 不具合の修正。** 不変条件の違反も AI レビューの指摘も、1 件ずつ別チケットで直す。
- **AI レビューの指摘を git-forum へ自動で起票すること。** 起票するのは利用者が承認した指摘だけ。
- **ヘルプ行に書かれたキーが実際に効くかの CI 検査。** 「効いた」の判定に解釈が入るため、AI レビューの点検項目として扱う。
- **TUI の描画性能や応答時間の測定。**

## Inputs / Outputs

### 用語

- **モード**: 入力の解釈を決める状態。`View`（List / ThreadDetail / NodeDetail / CreateThread / EditThreadBody / CreateNode / EditNodeBody / CreateLink）に、List のフィルタバー表示中、テキスト選択モード（`S` キー）、破棄確認、エラー表示の 4 つを加えたもの。
- **フォームの未保存入力**: 作成フォームで利用者が打ち込んだ自由記述のテキスト。スレッドのタイトル・タグ・本文、ノードの本文、手入力のリンク先が該当する。一覧から選ぶ項目（lifecycle、ノード種別、リンクの relation など）は含めない。現行の `has_unsaved_form_input` はタグを見ていないので、この定義とは一致しない。

### A. 不変条件スイート

**入力**

- **フィクスチャのリポジトリ**: テンプレートを 1 度だけ `StepClock`（`src/internal/clock.rs`）で作り、ケースごとに一時ディレクトリへ複製して使う。スレッドとノードの ID には乱数が入るので、テンプレートを作る間は、テスト用のビルドにだけある差し替え口（`src/internal/id.rs` の `TEST_NONCE`）で乱数を数え上げに替え、ID も毎回同じにする。B のドライバも同じテンプレートを使う。操作がスレッドの作成やノードの解決でリポジトリを書き換えるため、ケース間で状態を持ち越さない。テンプレートには次を必ず含める。
  - lifecycle 3 種（proposal / execution / record）と、複数の status のスレッド
  - 各種ノード（comment / objection / action など）と、返信の入れ子
  - スレッド間のリンク
  - ビューポートより長い本文、Markdown の表、CJK 文字と絵文字を含むタイトルと本文
  - 一覧には残っているが、実体が消えたスレッドの行。TUI が一覧を読み込んだあとに別のプロセスがスレッドを消し、まだ一覧を更新していない状況を再現する。この行を開くとエラー表示になる。正常なリポジトリで利用者がエラー表示に行き着く経路は、コードを読んだ範囲ではこれしか見つかっていない（開いているノードの reopen も、手入力のリンク先も、エラーにならない）
  - status と返信の入れ子は、TUI に書き込む手段がないので、作ったスナップショットを直接書き換えて用意する
  - これとは別に、スレッドが 0 件のリポジトリ
- **操作の種類**:
  - キー: `input.rs` が扱う全キー（`q Q j k f c r y l m S z t e x o R`、Space、Enter、Esc、Tab、Backspace、矢印、PageUp/PageDown/Home/End、Ctrl-S、Ctrl-C）と、フォーム入力用に、どのキーにも割り当てられていない文字（ASCII と CJK）
  - マウス: 左クリック、ホイール、ドラッグ。座標は、描画時に記録されたクリック領域（`UiRects`）の内側を優先して選び、フレーム内の任意の点も混ぜる
  - リサイズ: 端末サイズの集合 S の中での変更
  - 深いモードに入るための定型の操作列（例: `c` → Tab ×3 → Enter で EditThreadBody）を、生成する操作列の先頭に混ぜる
- **端末サイズの集合 S**: 少なくとも 1×1、各モードの最長のヘルプ行より狭い幅、80×24、200×60 を含む。
- **ケース数**: 既定値は CI の所要時間の予算から決める（Performance / Safety を参照）。手元では `PROPTEST_CASES` で増やして長く回せる。
- **シード**: 既定は固定値で、CI では毎回同じ操作列が生成される。`TUI_UX_SEED`（u64 または `random`）で変えられる。失敗したときは、再現に使う `TUI_UX_SEED` と `PROPTEST_CASES` の値を出力する。
- **並列実行**: ケースを 8 個の proptest の runner に分け、それぞれ別のスレッドで動かす。各 runner の乱数はシードと runner の番号から決まる。分割数はコア数によらず固定なので、同じシードとケース数なら、どのマシンでも同じケースが生成され、同じ判定になる。保存済みの回帰ケースを再生するのは runner 0 だけで、見つけた失敗はどの runner も保存する。縮小の回数の上限は、全体のケース数の 4 倍（proptest が 1 つの runner に自動で与える値と同じ）。失敗した runner がいくつあっても、それぞれの最小のケースを出力する。マウスとキーの比較（AT-14）も、表 M の行を最大 8 個のスレッドで分けて動かす。

**テスト用の内部構造（公開 API ではない）**

- `run_app` にあるイベント 1 件分の処理（info 表示の消去、破棄確認の y/n、エラー表示の解除、`handle_key`/`handle_mouse` の呼び出し、エラーからエラー表示への変換）を 1 つの関数（以下 `dispatch_event`）に切り出す。戻り値は「継続」「終了」「外部エディタの要求（thread id つき）」のいずれか。`run_app` はこの関数だけを呼び、外部エディタの起動と自動更新は `run_app` 側に残す。挙動は変えない。
- 外部への副作用（クリップボードへのコピー、マウスキャプチャの切り替えによる標準出力への書き込み）を差し替えられるようにする。本番は現行どおりの実装を、テストは呼び出しを記録するだけの実装を使う。
- 不変条件の検査関数は、描画後の画面バッファ、アプリの状態、直前のイベント、`dispatch_event` の戻り値を受け取る純粋関数とする。
- ケースを実行する関数は、イベント処理と描画の関数を引数に取る。スイートは `dispatch_event` と本番の描画関数を渡し、AT-2 の自己テストは壊れた関数を渡す。
- スイートは `src/internal/tui/` 配下の `#[cfg(test)]` モジュールに置く。TUI の内部モジュールは crate の外から見えず、`TEST-POLICY.md` の対象は `tests/` だけであるため。

### B. AI による探索的 UX レビュー

**入力**

- **ドライバ** `scripts/tui-ux/drive.py`（uv script。依存は pexpect 4.9.0 と pyte 0.8.2。手元のデモ録画スクリプト `scripts/demo/record.py` と同じ版だが、このスクリプトはリポジトリに入っていない）
  - 引数: git-forum のバイナリ、フィクスチャ名（`full` / `empty`）、端末サイズ、キー列ファイル、出力ディレクトリ
  - 実行のたびに、`./tmp/` の下へ使い捨てのリポジトリを新しく作る。中身は A と同じフィクスチャのテンプレートで、無視指定のテスト `export_fixture`（`src/internal/tui/ux_fixture.rs`）を cargo で実行して書き出す。そのため cargo とテストバイナリが要る。ID と日時は毎回同じ。
  - TUI の環境: 個人の Git 設定を読まない（`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_NOSYSTEM=1`）。`PATH` には `git`、`git-forum`、`true` へのリンクだけを置いたディレクトリを使い、クリップボードのコマンドを含めない。外部エディタ（`EDITOR`、`VISUAL`）は内容を変えずに終わる `true`。`HOME` と `TMPDIR` は実行ごとのディレクトリの中。既存のリポジトリを指定する引数は持たない。
  - キー列ファイルは 1 行に 1 操作: キー名（`j`、`Enter`、`Esc`、`Ctrl-s` など）、`text:<文字列>`、`resize:<W>x<H>`、`click:<x>,<y>`、`dblclick:<x>,<y>`、`scroll:up@<x>,<y>` / `scroll:down@<x>,<y>`。座標は画面テキストの桁と行で、0 から数える。空行と `#` で始まる行は読み飛ばす。
  - 操作のたびに、画面が落ち着くまで待つ。TUI は画面が変わらなくてもカーソル制御のシーケンスを約 105 ms ごとに書き続けるので、出力が止まるのを待つ方法は使えない。画面の文字とハイライト（背景色付きか反転表示のセル）が 300 ms 変わらなければ落ち着いたとみなし、1 操作に 10 秒かかっても落ち着かなければタイムアウトとする。
    - 2026-09-23 の計測（開発機を占有、デバッグビルド、80×24 から始める 6 回の実行で計 105 ステップ。キー、文字入力、フォーム、フィルタ、クリック、ダブルクリック、ホイール、リサイズを含む）: 操作から画面の最後の変化までは最大 58 ms（起動直後）。閾値の 300 ms は、その約 5 倍で、書き込みの周期の約 3 回分。
    - 同じ計測で、80×24 から 60×20 に縮めると、一覧が 2 通りの列配置を交互に描き続けて落ち着かないことが分かった（起動時から 60×20 なら落ち着く）。これは TUI の不具合として扱い、ドライバはタイムアウトとして記録する。
- **報告前の確認スクリプト** `scripts/tui-ux/verify.py`: レビューの `findings.json` を読み、指摘ごとにキー列をドライバで再生し、引用した文字列が該当の `step-NNN.txt` のどれか 1 行にあるかを確かめて、`引用行あり` / `引用行なし` / `再生失敗` を出す（Failure modes 9）。
- **ドライバの受け入れ確認** `scripts/tui-ux/selftest.sh`: AT-10〜AT-12 を確かめる。
- **手順書** `doc/tui-ux-review.md`。エージェント向けに次を定める。
  - 利用者として行う課題（例: execution のスレッドを作る、objection を付けて解決する、フィルタで目的のスレッドを探す、ノードからリンクを張る）
  - 点検項目: キーの見つけやすさ、ヘルプ行に書かれたキーが実際に効くか、戻る/取り消しの文言の一貫性、操作に対する反応の有無、狭い幅での表示の欠け、CJK の表示崩れ、エラーメッセージから次の手が分かるか、取り消せない操作の前に確認があるか、マウスでできることとキーでできることの差、クリックできそうに見えて反応しない表示
  - 端末サイズ: 80×24（INV-2 が保証する最小サイズ）と、それより狭い 60×20 の 2 種類。狭い幅は不変条件の対象外だが、表示が欠けても使えるかを判断するために見る
  - 報告の書式と、報告前の確認手順（Failure modes 9）

**出力**

- ドライバ: 出力ディレクトリに、操作ごとの画面テキスト `step-NNN.txt`（`step-000.txt` は起動直後）、ハイライトの位置 `step-NNN.hl.txt`（背景色付きか反転表示のセルの範囲ごとに `<行>,<開始桁>-<終了桁>: <文字>`。TUI は選択中の行を背景色だけで示すので、画面テキストには選択が現れない）、実行記録 `run.json`（キー列、端末サイズ、バイナリのバージョン、フィクスチャ名、終了コード、標準エラー出力、タイムアウトの有無、ドライバが Ctrl-C で終了させたか、操作ごとの画面が落ち着くまでの時間）。キー列を最後まで送っても TUI が動いていれば、Ctrl-C を最大 2 回送って終了させる（INV-4）。
- レビュー: `./tmp/tui-ux-review/<日時>/report.md` と、端末への要約。指摘ごとに、ID、重大度（blocker / major / minor / nit）、該当する点検項目、観察した内容（`step-NNN.txt` の該当行の引用）、再現用のキー列ファイルと端末サイズ、改善案を書く。
- git-forum へは書き込まない。利用者が選んだ指摘だけを、別途 `--as ai/<agent>` で起票する。

### Public API surface

なし。CLI のフラグ、サブコマンド、設定キーは増やさない。`dispatch_event` と副作用の差し替え口は `src/internal/tui/` の非公開要素とする。dev-dependency に `proptest` を加える。

## Failure modes

1. **導入時点の既存違反でスイートが失敗する**
   - (a) 契機: 現行コードが不変条件を満たしていない。
   - (b) 検出: スイートの失敗。
   - (c) 見え方: マージできない。
   - (d) 対処: 違反ごとにチケットを起票し、除外リストに登録する。登録した最小再現操作列は毎回そのまま再生し、違反が再現しなくなったら「除外が古い」としてテストを失敗させる。除外が残り続けて問題が見えなくなるのを防ぐため。
2. **一部のモードに到達せず、検査が効いていない**
   - (a) 契機: ランダムな操作列では、EditNodeBody や破棄確認のような深いモードにほとんど入らない。
   - (b) 検出: モード別の到達回数の集計。
   - (c) 見え方: 既定のケース数で到達回数が 0 のモードがあれば、テストが失敗する。
   - (d) 対処: 定型の前置き操作列を生成器に加える。
3. **検査関数の誤りで違反を見逃す**
   - (a) 契機: 不変条件を判定するコードの誤り。
   - (b) 検出: 検査関数ごとの自己テスト（AT-2）。違反する状態を手で作って渡し、違反と判定されることを確かめる。
   - (c) 見え方: 自己テストの失敗。
   - (d) 対処: 自己テストが通るまでスイートの結果を信用しない。
4. **テストの経路と本番の経路がずれる**
   - (a) 契機: `run_app` が `dispatch_event` を通さずに入力を処理するコードを持つ。
   - (b) 検出: ソースを走査する監査テスト（AT-6）。既存の `syn` を使う監査テストと同じ方式。
   - (c) 見え方: 監査テストの失敗。
   - (d) 対処: 入力処理を `dispatch_event` に戻す。
5. **テストが開発者の環境に副作用を出す**
   - (a) 契機: `y` による開発者のクリップボードの上書き。`S` などでマウスキャプチャを切り替えるエスケープシーケンスが、`cargo test` を実行中の端末へ直接書かれる（テストハーネスは `print!` しか捕捉しない）。外部エディタの起動。開発者のリポジトリへの TUI 状態ファイルの保存。
   - (b) 検出: 監査テスト（AT-6）と、記録用の副作用実装への呼び出しの記録（AT-7）。
   - (c) 見え方: 起きれば、テスト後に開発者のクリップボードや端末の状態が変わる。
   - (d) 対処: 副作用は差し替え口を通す。TUI 状態ファイルのパスは一時ディレクトリに向け、外部エディタの要求は `dispatch_event` の戻り値として返すだけにする。
6. **結果が実行のたびに変わる**
   - (a) 契機: 自動更新の時刻依存、`HashSet` の走査順、環境変数、実時刻。
   - (b) 検出: 同じシードで 2 回実行した結果の比較（AT-8）。
   - (c) 見え方: CI が不安定になる。
   - (d) 対処: `dispatch_event` に自動更新を含めない。フィクスチャは `StepClock` で作る。ケースの途中で TUI が作るスレッドの時刻は実時刻になるが、不変条件は時刻の表示に依存しない。
7. **CI の所要時間が予算を超える**
   - (a) 契機: ケース数 ×（フィクスチャの複製 + 操作の処理）。
   - (b) 検出: CI の実行時間。
   - (c) 見え方: マージまでの待ち時間が延びる。
   - (d) 対処: 既定のケース数を下げ、長い探索は手元で `PROPTEST_CASES` を上げて行う。
8. **ドライバが起動しない、または画面が落ち着かない**
   - (a) 契機: バイナリがない、uv や依存を入れられない、TUI が描画し続ける。
   - (b) 検出: ドライバの終了コードと `run.json`。
   - (c) 見え方: 待ち時間の上限を超えたら、その時点の画面を保存し、`run.json` に timeout と記録して非 0 で終了する。
   - (d) 対処: エージェントは timeout そのものを指摘として報告する（応答しない画面は UX 上の問題でもある）。
9. **AI レビューが根拠のない指摘をする**
   - (a) 契機: 画面にない内容を指摘する、再現しない指摘を書く。
   - (b) 検出: 報告の前に、指摘ごとに再現用のキー列をドライバで再生し、引用した行が該当の `step-NNN.txt` にあることをスクリプトで確かめる。
   - (c) 見え方: 確かめられなかった指摘は本文から外し、「未確認」の節に分けて列挙する。
   - (d) 対処: 未確認の指摘は起票の候補にしない。
10. **AI レビューが開発者のリポジトリに書き込む**
    - (a) 契機: エージェントが手元のリポジトリで直接 `git forum tui` を起動する。このリポジトリには、`Created in TUI` という題で作られ却下されたスレッドが 3 件ある（`vmv1l4st`、`wj05n02e`、`itqtdgtp`）。
    - (b) 検出: レビューの前後で、開発者のリポジトリの `git for-each-ref refs/forum` の出力を比べる。
    - (c) 見え方: 一致しなければ、報告の冒頭にその旨を書き、利用者に知らせる。
    - (d) 対処: 手順書は、ドライバを通さない起動を禁じる。
11. **マウスとキーの比較が、実時刻で決まる値の違いで失敗する**
    - (a) 契機: 送信の行のクリックと Enter がそれぞれスレッドやノードを作ると、ID と日時が実時刻で決まるので、2 つの結果は完全には一致しない。
    - (b) 検出: INV-9 の比較の失敗。
    - (c) 見え方: 挙動は同じなのにテストが失敗する。
    - (d) 対処: 作られたものの ID と日時は比べない。代わりに、どのビューに移ったかと、作られたものの題名・本文・種別を比べる。
12. **表 M が実装とずれる**
    - (a) 契機: マウス処理を変えたのに、表 M とテストの対応表を更新しない。
    - (b) 検出: 新しいクリック領域は、ランダムな操作列から INV-10 の検査に届く。対応表にない領域が描画されたら、INV-10 の検査がそれを「対応表にないクリック領域」として失敗させる。
    - (c) 見え方: テストの失敗。
    - (d) 対処: 表 M とテストの対応表を、マウス処理の変更と同じコミットで更新する。

## Performance / Safety

- **CI の所要時間**: 予算は「不変条件スイートが、開発機を占有した状態の手元の計測で 10 秒以内」。既定のケース数は 64。
  - 2026-09-23 の計測: 1 ケースあたり約 97 ms、64 ケースで 6.2 秒。スイートは 1 つのテストで、並列には動かない（32 コアの開発機を占有し、同じシードで 2 回計測）。
  - 同じ日の `cargo test` 全体は 4.18〜4.25 秒（`eae18e1`、ビルド済みの状態）。
  - INV-2〜INV-11 の検査と INV-3 の戻り操作を入れた後（同じ日、同じ条件）: 64 ケースで 6.97 秒と 6.99 秒（1 ケースあたり約 109 ms）。段階ごとの内訳（計時を入れた別の 1 回、合計 7.06 秒）は、フィクスチャの複製とスレッド一覧の読み込み 2.96 秒、描画 2.72 秒、イベント処理 1.20 秒、検査 0.03 秒。1 回の実行で `git` のプロセスを 6,666 回起動する（フィクスチャの作成を含む）。
  - 並列化した後（同じ日、同じ条件）: スイートは 64 ケースで 1.42 秒、マウスとキーの比較は 11.80 秒から 2.06 秒。`cargo test` 全体は 16.1 秒と 15.9 秒から、6.58 秒、6.58 秒、6.56 秒になった（別の計測の 1 回だけ 11.7 秒で、原因は特定できていない）。
  - 並列化した後の生成器で、既定のシードでは、16 ケースだと AT-3 が失敗する（NodeDetail、EditThreadBody、EditNodeBody に届かない）。32 ケースでも EditNodeBody に届かない。64 ケースで全モードに届くが、EditNodeBody へは 2 回だけで余裕が小さい。128 ケースなら EditNodeBody へ 29 回届く。既定の 64 ケースは、シードが固定なので毎回同じ結果になる。ほかのシードで 64 ケースが全モードに届くかは確かめていない。
  - 手元の計測が 10 秒を超えたら、さらに最適化を入れる。
  - CI のランナーはコア数が少なく、キャッシュがなければビルドも毎回かかるので、手元の値はそのまま CI には当てはまらない。
- **決定性**: 同じシードとケース数なら、同じ操作列が生成され、同じ判定になる。
- **開発者環境の保護**: 不変条件スイートは、開発者のクリップボード、端末、外部エディタ、リポジトリに触れない。AI レビューは `./tmp/` の外に書き込まない。
- **匿名化**: 指摘を起票するときは、報告に含まれるホームディレクトリのパスやユーザー名をマスクする。

## Acceptance tests

1. **AT-1 スイートが通る**: 除外リストを含めた状態で、不変条件スイートのテスト（`cargo test` でモジュール名を指定して実行）が成功する。除外リストのどの項目にも git-forum のチケット ID が付いている。
2. **AT-2 検査関数の自己テスト**: INV-2〜INV-12 のそれぞれについて、違反する画面バッファや状態を手で組み立てて検査関数に渡すと、その INV の違反として報告される。例: 一覧の選択を表示件数と同じ値にする → INV-6。表 H の文字列を含まない List の画面 → INV-2。INV-1 は、panic する描画関数を渡すと違反として報告されることで確かめる。INV-3 は、ThreadDetail で Esc を無視するイベント処理を渡すと INV-3 の違反として報告されることで確かめる。INV-9 と INV-12 は、マウス側とキー側の結果が異なる行（何もしないマウス操作と下矢印、反応しないヘルプ行のクリックと Esc）を比較に渡すと食い違いとして報告され、両側が同じ行では報告されないことで確かめる。
3. **AT-3 全モードに到達する**: 既定のケース数の実行で、「用語」に挙げたモード（List、フィルタバー、ThreadDetail、NodeDetail、CreateThread、EditThreadBody、CreateNode、EditNodeBody、CreateLink、テキスト選択、破棄確認、エラー表示）のすべてに 1 回以上到達する。到達しないモードがあればテストが失敗する。
4. **AT-4 失敗時の出力**: 手元で ThreadDetail の Esc を無効にする変更を一時的に入れて実行すると、INV-3 の違反として、最小化した操作列、端末サイズ、シード、画面テキストが出力される。変更を戻すと成功する。手動の確認として、実行結果を PR に記録する。
5. **AT-5 挙動を変えない切り出し**: `dispatch_event` を切り出したあと、既存の TUI ユニットテストが変更なしですべて通る（切り出し前の件数を記録し、同数であることを確かめる）。INV-8 の各場合（エラー表示中の任意のキー、破棄確認中の `y`、`Y`、その他のキー）を `dispatch_event` 経由で確かめる個別のテストが通る。
6. **AT-6 監査テスト**: (a) `run_app` の本体に `handle_key` と `handle_mouse` の直接呼び出しがない。(b) `src/internal/tui/input.rs` と `src/internal/tui/state.rs` に、`std::io::stdout`、`execute!`、`Command::new`、`copy_to_clipboard` が現れない。どちらの監査も、違反する 1 行を一時的に加えると失敗することを確認済みであること。
7. **AT-7 副作用の記録**: スイートの環境で、List でスレッドを選んで `y` を押すと、記録用の実装にクリップボードの呼び出しが 1 件残る。中身は選択中のスレッド ID を `display_thread_id` で表示用にした文字列（ADR-014）。ThreadDetail で `S` を押すとマウスキャプチャ無効化の呼び出しが 1 件残り、続けて任意のキーを押すと有効化の呼び出しが 1 件残る。
8. **AT-8 決定性**: 同じシードで 2 回実行すると、モード別の到達回数と成否が一致する。
9. **AT-9 古い除外の検出**: 実際には違反しない操作列を持つ項目を除外リストに加えると、テストが「除外が古い」という理由で失敗する。
10. **AT-10 ドライバの基本動作**: 同梱のサンプルキー列（`Enter` → `Esc` → `q`）でドライバを実行すると、終了コード 0 で終わり、`step-001.txt` に `[esc/q]back`、`step-002.txt` に `[q]quit` が含まれ、`run.json` にキー列・端末サイズ・バイナリのバージョンが記録される。
11. **AT-11 ドライバの隔離**: AT-10 の実行前後で、開発者のリポジトリの `git for-each-ref refs/forum` の出力が一致する。ドライバが作ったリポジトリは `./tmp/` の下にある。
12. **AT-12 ドライバの再現性**: 同じキー列を 2 回再生すると、日時の表示部分を除いて、すべての `step-NNN.txt` が一致する。再生中に TUI が作ったスレッドやノードは実時刻と乱数で ID が決まるので、それを表示する画面は比べない。AT-10〜AT-12 は `scripts/tui-ux/selftest.sh` が確かめる。
13. **AT-13 手順書どおりのレビュー**: エージェントに `doc/tui-ux-review.md` を渡して実行させると、`report.md` ができ、各指摘に再現用のキー列が付き、報告前の確認スクリプトが全指摘について「引用行あり」を返す。AT-11 と同じ方法で、git-forum への書き込みがないことを確かめる。手動の受け入れ確認とする。
14. **AT-14 マウスとキーの一致**: 表 M の「キー操作なし」以外の各行について、フィクスチャから同じ状態を 2 つ用意し、片方にマウス操作、もう片方に対応するキー操作を与えると、INV-9 で比べる状態が一致する。行ごとに 1 つのテストとし、決まった操作列で行う（ランダムにはしない）。
15. **AT-15 ラベルの一致**: 不変条件スイートは、描画のたびに INV-10 を確かめる。自己テストとして、ラベルの文字列を含まない領域を渡すと INV-10 の違反と判定され、対応表にないクリック領域を渡すと「対応表にないクリック領域」と判定される。
16. **AT-16 オーバーレイ中のクリック**: CreateThread で題名を入力して Esc を押し、破棄確認を出す。その状態で送信の行をクリックすると、確認が閉じ、スレッドは作られず（`list_threads` の件数が変わらない）、題名が残る。エラー表示中のクリックは、表示を消すだけで、ビューと選択を変えない。
17. **AT-17 戻る表示のクリック**: 表 H の Esc 系のヒントが表示される各モード（ThreadDetail、NodeDetail、フィルタバー、CreateThread、CreateNode、CreateLink、EditThreadBody、EditNodeBody）で、その文字列の上をクリックした結果が、Esc を押した結果と一致する（INV-9 と同じ比べ方）。
